# Agent Skill authorization, sharing, identity and Workspace manifest

**Status:** Accepted design decisions, 2026-10-14; authoritative on these subjects for [skills.md](./skills.md), [authentication.md](./authentication.md), [web-ui.md](./web-ui.md) and implementation tickets #3854, #3855, #3857, #3858, #3861. Stages #3854–#3858 have now passed focused review and are closed in still-draft #3850, including CLI/Workspace synchronization, capture, Retry / Re-check and grantable Workspace access. Do not silently implement future #3861 sharing/installations as part of #3855. Existing Registry/Storage APIs stay generic; no skill-only Registry/Storage endpoint or shared bucket is introduced. The distinct **local computer multi-profile/agent-harness** sync contract is [local-agent-skill-sync.md](./local-agent-skill-sync.md) (accepted 2026-10-18; implemented in reviewed Stage #3855).

> **Principle:** **Skill discovery is based on the intended user; skill access is based on authorization; skill synchronization is optional to Workspace availability.**

> **Revised 2026-10-23 (#3869 / #3870):** OPA no longer validates a publication's deterministic identity, and Agent Services is the only non-admin writer of Agent Skill records. Generic `object/record/*` writes on Agent Skill records are limited to admins and unconstrained generic grants, which now apply to every record. See [agent-skill-authorization-model.md](./agent-skill-authorization-model.md) for the revised model and the use-case table. Passages below marked *Revised* are updated accordingly.

## Typed records and identity

| Registry record | Fields | ZIP and immutable identity |
| --- | --- | --- |
| Published user skill | `agent-skill.type = "user"`, **required** `agent-skill.userId`, `access-control` | One source ZIP linked to publication ID `agent-skill-<userId>-<name>` |
| Published system skill | `agent-skill.type = "system"`; **no** `userId`; `access-control` | One source ZIP linked to `agent-skill-system-<suffix>`, where name is `system-<suffix>` |
| Installed shared skill | `agent-skill-installation.userId`, `sourceSkillId`, optional `alias`, `access-control`; **no** `agent-skill` aspect | No ZIP; ID `agent-skill-<userId>-<effective-name>`; source remains another user's published skill |

Rename the old `agent-skill.scope` publication field to immutable **`agent-skill.type`** with `system|user`; do not represent installation as a third value of this field. Names from `SKILL.md` are immutable, regex `^[a-z0-9]+(?:-[a-z0-9]+)*$`, max 46 characters; system names start `system-`; user/installation names cannot, and runtime names are reserved. Preserve PENDING/READY/DELETING publication state, ZIP checksum, immutable creator and archive linkage.

**`userId` and `access-control.ownerId` have distinct meanings.** `userId` names the target user/namespace and is required for user publications and installations, immutable, **and must match the UUID embedded in the deterministic record ID**. `access-control.ownerId` is the Registry record owner used for permission constraints. Ordinary MVP creation requires `userId == ownerId == authenticated actor UUID`. Future explicitly permitted delegated provisioning may allow them to differ, but `userId` is **never itself permission to read**; the intended user still needs OPA access. For system publications, no `userId`. Enforce deterministic ID/userId consistency on all Agent Services creation, update, read and Workspace manifest resolution paths, fail closed for malformed records. Do not derive ownership from the ID, or infer target user from ownerId.

Preserve deterministic per-user ID uniqueness across own publications and installed shared skills; owner/alias/name changes must not bypass identity restrictions. For an installation **alias rename = uninstall then reinstall** under a new ID, requiring both install/delete and install/create permissions. Register install/update for later non-identity settings; initially it cannot rename an alias.

## Registered authorization resources, operations and stock roles

MAGDA Authorization DB registers resources and their CRUD operations:

```text
object/agentSkill/system/{create,read,update,delete}
object/agentSkill/user/{create,read,update,delete}
object/agentSkill/install/{create,read,update,delete}
agentWorkspace/access
```

**Do not register or implement `object/agentSkill/*/read`.** Use the Agent Services Workspace manifest API below. Operations remain independently grantable; a user may install without delete, or manage system skills without global MAGDA administrator status.

Ship **unassigned** configurable stock roles (do not auto-grant them to all Authenticated Users; retain admin-only initial Workspace access). Use generated or fixed UUIDs in DB migrations as convenient; app logic should depend on stable operation URI/semantic role identification, not hardcoded generated UUIDs.

| Stock role | Permission operations | Constraint | allowExemption |
| --- | --- | --- | --- |
| Agent Workspace Users | `agentWorkspace/access` | none | false |
| Agent Workspace Users | `object/agentSkill/system/read` | OrgUnit | true |
| Agent Workspace Users | `object/agentSkill/system/read` | pre-authorised | true |
| Agent Workspace Users | `object/agentSkill/user/create,read,update,delete` | user ownership | false |
| Agent Workspace Users | `object/agentSkill/user/read` | OrgUnit | true |
| Agent Workspace Users | `object/agentSkill/user/read` | pre-authorised | true |
| Agent Workspace Users | `object/agentSkill/install/create,read,update,delete` | user ownership | false |
| Agent Skills Admins | `object/agentSkill/system/create,read,update,delete` | none | false |

The two OrgUnit/pre-authorised read permissions (for each publication type) have **`allowExemption=true`** so setting source record `access-control.constraintExemption=true` permits anyone holding the matching exemption-capable read operation, without satisfying the specific OrgUnit or pre-authorised constraint. A pre-authorised permission without a matching **record permission ID** does not itself grant access to private publications. Owners receive their own user read via ownership permission. A system-skills admin role does not imply `agentWorkspace/access`.

**Publication type immutability at the supported API:** Agent Services must preserve `agent-skill.type`, target `userId`, deterministic record ID, archive linkage, name, owner and creator fields across create, replace, delete and recovery; reject a `user` ↔ `system` transition **even when the caller holds both typed permissions**. Typed OPA policy enforces scope-specific permissions for the actual/proposed concrete record. *Revised:* identity validation (deterministic ID, name rules, archive key) is Agent Services' job, not OPA's, and because Agent Services is the only non-admin writer of Agent Skill records, ordinary users can't bypass these invariants through the generic Registry API (only admins and unconstrained generic grant holders, who are trusted, can write skill records directly). Bulk Registry mutations authorise every record's current and proposed state (#3870). See [agent-skill-authorization-model.md](./agent-skill-authorization-model.md). Installation records remain a distinct aspect, not a type transition.

**Important OPA privacy rule:** use typed **skill-specific** read rules, not the generic `verifyRecordPermission` OrgUnit-read fallback for an **absent/empty** orgUnitId. Skill read requires (a) matching owner grant, (b) an actually matching non-empty OrgUnit and user's managed org unit, (c) a matching permission ID included in `access-control.preAuthorisedPermissionIds` and assigned to the user, (d) `constraintExemption == true` plus a permission with `allowExemption == true`, or (e) applicable unconstrained management/admin read. Missing OrgUnit alone is not a grant. System writes are allowed to trusted non-admin users **only** through scope-specific management grants. Admin entrypoint's existing global bypass remains.

**Reserved Agent Skill ZIP read boundary (accepted Stage #3854 / commit `046190ec3`; *revised* #3870):** The Storage OPA policy identifies both exact-prefix namespaces, `agent-services/skills/system-skills/` and `agent-services/skills/user-skills/`, **from the trusted object key**. For `storage/object/read` within either namespace, owner, matching-OrgUnit and legacy missing/empty-OrgUnit Storage grants **must not bypass the record's read rules** (*revised:* unconstrained Storage grants, being deliberate trusted grants, apply). Allow a non-admin read only for an existing Storage object whose trusted `recordId` and key match an `agent-skill` Registry record the **real caller** can read (typed source-read, or an unconstrained generic record read). Storage OPA fails closed when the required record context or linkage is absent or mismatched; it no longer validates the publication's identity: Agent Services and Workspace sync validate the publication, and the downloaded ZIP content/checksum, and reject invalid archives. A record link alone is not sufficient authorization. The existing global-administrator entrypoint override remains available for trusted internal lifecycle inspection. Ordinary legacy dataset, distribution and standalone Storage reads (including historic #3412/#3426 missing/empty OrgUnit semantics) are unchanged. *Revised:* writes (upload/delete) under the reserved prefixes are limited to Agent Services (as an admin), admins and unconstrained grants: constrained Storage permissions don't apply there, an object there can only be linked to its own Agent Skill record, and linked archive writes require the generic record operation, which typed Agent Skill grants alone don't have. Agent Services uploads and deletes archives with its internal session, so an archive's Storage owner isn't part of its link to the publication. See [agent-skill-authorization-model.md](./agent-skill-authorization-model.md).

*Revised (#3870):* In `object/record/allow.rego`, a **concrete published skill record** is read with the typed `object/agentSkill/{system|user}/read` rules (type derived from actual record aspects, **not** the caller's URL), and is written only by admins and unconstrained generic `object/record/<operation>` grants; constrained generic grants never apply to it, and typed Agent Skill grants can't write it through the generic Registry API. Unconstrained generic grants (deliberate, trusted; no built-in role has one) apply to every record, including skill records. Reserve `agent-skill-installation` for fail-closed handling (except unconstrained generic grants) until #3861 implements installation-specific typed dispatch. Agent Services enforces identity/lifecycle invariants and the real caller's typed operation before every internal-session write. All rules use only literal comparisons, so no partial decision contains untranslatable built-in calls. See [agent-skill-authorization-model.md](./agent-skill-authorization-model.md).

## Sharing: reuse Access Group features, no skill-source copying

Access Group currently auto-creates a **pre-authorised permission + role**, assigns selected users to the role and attaches a group-specific permission ID to a source Registry record's `access-control.preAuthorisedPermissionIds`. Its existing backend is limited to `object/record` operations and dataset attachment APIs. Extend/generalise its resource/operation configuration and linking to **`object/agentSkill/user/read`** (optionally constrained system sharing under suitable publisher permissions) instead of granting broad `object/record/read`. Validate the publication owner's/sharer’s actual authority before writing grant IDs; use existing user-ID input, Access Group UI/management components and API patterns in a simplified Share Skill interface. Recipient user UUID can be obtained from the account page. **Use group-specific permission ID**, not the stock role's global pre-authorised read permission ID, when attaching explicit grants.

Access Group membership is not installation. Recipients with source-read can *discover* shared READY publications, then use owner-constrained `object/agentSkill/install/create` to explicitly install an authorized other-user source. Installation record access must **never** confer original source ZIP access: source Storage object's linked `recordId` is the **published user skill ID**, not the installation ID. Recheck source `object/agentSkill/user/read` before installation, on ZIP download and every Workspace manifest resolution. On sharing revocation, recipients' installations remain uninstallable but the source is no longer downloadable/syncable. A readable but not installed shared skill is **not installed automatically**.

**Registry `aspectQuery` inequality is supported:** `agent-skill.userId:!<currentUserUUID>` denotes a publication intended for someone *other* than the caller; the operator is `:!`, **not `!=`**. The **Shared Skills / All available** query uses `aspect=agent-skill`, `agent-skill.type:user`, `agent-skill.userId:!<currentUserUUID>`, `agent-skill.state:READY`, plus normal Registry/OPA read filtering; **My Skills** instead uses `agent-skill.userId:<currentUserUUID>`. For the default Agent Skills **All** catalogue, use a **single Registry-side `aspectOrQuery`** predicate combining `type=system` OR `userId=<currentUserUUID>`, together with `state=READY` and OPA, so keyset pagination remains correct. For the future Workspace manifest, separately paginate visible system and own-user sources and merge the effective set; never treat `type=user` as implicitly owned; uninstalled other-user readable sources belong to Shared Skills. Negation can match records with a missing field in the SQL representation; always validate userId presence, ID match and source permissions after query, and do not infer access from `:!` alone.

Stage #3861 owns Access Group generalization, sharing grant lifecycle, installation aspect/API/UI, and alias-specific sync. Implemented Stage #3854 established typed published-resource operations, constraints and stock roles, and closed Stage #3855 provides the manifest abstraction for later installations; do not expand the current implementation stage into full #3861 without explicit re-scoping.

## System skill visibility and management UI

**Policy choice:** `constraintExemption=true` is the accepted **default for newly published system skills**; system skills are intended for broad reuse. This does not grant anonymous access: only users with an applicable typed `object/agentSkill/system/read` permission and `allowExemption=true` (or suitable other read authority) can read the source. A trusted publisher can later narrow the skill by clearing the exemption and choosing an OrgUnit and/or individual grants.

**UI specification:** See [web-ui.md — System skill access management](./web-ui.md#system-skill-access-management--public-by-default). Show checked **Public skill** checkbox with info-tooltip detailing actual permission scope; clearable OrgUnit tree picker; recipient user-UUID input and searchable/paginated granted-users table with per-recipient revoke, reusing the existing `OrgUnitDropDown` and `AccessGroupUsersPanel` patterns. Sharing uses typed **system/read** permission IDs, not a generic record read grant. Access grants are additive: an OrgUnit selection or named recipients do not limit an exempt/public skill until the checkbox is unchecked. Ensure publisher has real authorization to change source `access-control` fields, including adding/removing pre-authorised grants. Implement management UI in the appropriate UI/sharing stage, not as an implicit #3854 Stage-1 expansion.

## Agent Services permissions and internal lifecycle authority — accepted 2026-10-15

**Decision: Option 1.** The public Agent Services endpoint authorizes the **real caller** for exactly the typed, semantically requested operation. A caller permitted only `object/agentSkill/{system|user}/create` must be able to publish a new skill; `update` is sufficient to replace one, and `delete` is sufficient to remove one. `read` is required to read/list/download a source, **not implicitly required to create, update or delete**. Intermediate `PENDING -> READY` and `READY -> DELETING` transitions, retry recovery and internal record lookups must not add separate *caller* read/update permission requirements. Use the intended user's UUID/record ID and actual Registry state to determine the target independently of `access-control.ownerId`.

**Accepted internal principal:** Use MAGDA's existing built-in default system administrator, **`DEFAULT_ADMIN_USER_ID = "00000000-0000-4000-8000-000000000000"`**, imported from `magda-typescript-common/src/authorization-api/constants.ts` (avoid an independently copied magic UUID). Agent Services may mint a signed, short-lived **`X-Magda-Session` JWT** for this principal using its existing protected `jwtSecret`, like other trusted MAGDA server services. The default admin identity **is broadly privileged**: it is deliberately chosen here in preference to introducing a bespoke least-privilege role. Therefore the Agent Services typed caller-authorization, exact target/operation validation, and restricted usage of this JWT are **critical security boundaries**, not optional defence-in-depth.

**Execution contract:**
1. Authenticate/verify the caller's MAGDA session/API-key-derived identity. For a new skill derive `type`, `userId`, owner and deterministic ID from trusted caller identity + validated ZIP; for existing skill **fetch the actual record internally** (admin JWT if the caller has no `read`), validate the linked `agent-skill` aspect, immutable identity/name/type and current state, and do not disclose protected record details before authorization.
2. Ask OPA about the **caller**, with their own session and actual/proposed authoritative target, for the **one requested** `object/agentSkill/<type>/<create|update|delete>` operation. On denial, stop; never run privileged write steps. Do not let an admin JWT inadvertently determine authorization for the caller, and do not trust path/type/owner/recordId/Storage key supplied by the client. An early create check may guard upload admission; a post-validation check of the **same create** operation is acceptable for refreshed policy/record identity, but never require separate `update`.
3. Execute the *fixed, validated* Registry/Storage transaction-like lifecycle under the **caller JWT where that operation already works** and under the **server-minted default-admin JWT** for necessary internal reads, transitions, recovery and downstream operations that the caller may not independently perform. In particular, initialise the new Storage ZIP using the **real caller session where feasible**, so its canonical `magda-owner-id` is that actual publisher rather than the built-in admin; ensure linked record ID is the original publication ID. If the implementation instead uploads the first ZIP as admin, it **must first** demonstrate an existing, trusted Storage API mechanism to record the real original owner without client-forged metadata. Replacements must preserve the original Storage owner as guaranteed by #3853 even for different authorised system-skill publishers.
4. Preserve `access-control.ownerId`, `createdBy` and `updatedBy` as meaningful **real user** ownership/provenance: `createdBy` is immutable original publisher, `updatedBy` is the actual later actor; never silently use `DEFAULT_ADMIN_USER_ID` as these values. Continue version/concurrency, corruption/ZIP, retry/idempotency, operation-specific permission and owner/target protections.
5. **Use the minted admin JWT only inside trusted Agent Services-to-Registry/Storage calls**, for the necessary workflow, and never return it to browser clients, `mgd`, DSH or Sandbox; never persist it to Sandbox PVC, logs, telemetry, errors or user-visible responses. Mint with a bounded expiry and avoid unnecessary lifetime/reuse. The service's shared signing secret must remain protected. Prefer a narrowly encapsulated client/internal method for privileged workflow, **not** a generic user-accessible admin proxy. Read/list/download and Workspace manifest/source access remain authorised against the **caller** and do not use the privileged identity to bypass sharing.

**Tests required for Stage #3854:** create-only user and system-skill publisher, update-only, delete-only, and read-only identities; successful PENDING/READY and DELETING lifecycle without extraneous caller grants; denied/malicious caller cannot coerce privileged admin operations; inaccessible-existing-record update/delete permission check against actual record; missing/invalid/type-switched publication and wrong userId/owner fail closed; an original publisher retains Storage `magda-owner-id` after new publish and cross-publisher replacement; failure/retry and partial operations don't leak the signed JWT or permit cross-record writes. Direct Registry/Storage API OPA protections must not be weakened merely because Agent Services uses a trusted admin principal. *Revised (#3870):* Agent Services now writes all Agent Skill Registry records with the internal principal, after authorising the caller; direct generic Registry writes of skill records are limited to admins and unconstrained generic grants.

## Workspace manifest, best-effort synchronization and UI feedback

**Final source-failure distinction (2026-10-18):** The same local/Workspace reconciler **must not mutate installed skills** during an online attempt unless the authoritative manifest and all required current ZIPs are complete, authorized, downloaded/reused at matching checksum and verified. A failed current v2 download cannot substitute cached v1 (even with `--force`); preserve the last complete cache snapshot without adding durable `unresolved` markers, fail with actionable retry status and keep Workspace READY/DSH available. Once remote preparation succeeds, local content conflicts block **only affected installations**: independent clean replacement/removal, absent install and safe metadata repair proceed and give partial/nonzero status for remaining conflicts. Publish commands cache each successfully server-acknowledged exact ZIP, without marking a global manifest as freshly checked. Per-skill recovery verifies full digest before backup cleanup. [Full design](./local-agent-skill-sync.md).

**2026-10-18 accepted synchronization contract:** Both local computers and MAGDA-hosted Sandboxes use **the same [scan-based, copy-only Agent Skill reconciler](./local-agent-skill-sync.md)**. A real skill directory's root `.magda-skill-install.json` is the authoritative durable installation identity/baseline; **no central installation index or global journal/rollback**. The reconciler scans native roots, repairs clean exact-match marker loss, reinstalls absent desired skills, preserves modified conflicts without force and leaves completed skill updates intact on partial I/O failures. Unmarked dirs not in the current verified desired manifest are unrelated local data and ignored. The Workspace manifest still independently defines eligible **visible system + own + future installed shared** sources, while local computers include own plus recipient-installed shared (not system). **Non-blocking READY/DSH:** Manager can force-sync a genuinely fresh empty Sandbox; existing/reconnected user storage is not silently forced. #3857 user Retry/Re-check first requests confirmation then invokes Manager-owned `sync --force --workspace-status`; manual CLI `sync` or `sync --force` follows identical local user-intent rules and does not write Manager last-run status. Remote revocation removal requires successful authoritative reconciliation; modified non-forced copies can remain locally and must be reported, not counted as a clean successful removal.

**Important scope distinction:** The manifest described below is for a MAGDA-managed Agent Workspace Sandbox. It intentionally includes published **system** skills. On a user's local computer the accepted #3855 behavior is different: automatically activate **only own user publications**, and after #3861 explicitly installed shared user skills, from a per-instance/account verified library into one active profile's harness-visible projection. No automatic system-skill activation locally. See [local-agent-skill-sync.md](./local-agent-skill-sync.md).

Expose **`GET /api/v0/agent/skills/workspace-manifest`**, service method `getWorkspaceSkillManifest`, for Workspace initialization. This is **not** the browseable catalogue of all readable/installable skills. Fetch with the current user's trusted session using **separate paginated, permission-filtered Registry queries**:

1. All **visible READY system** publications: `aspect=agent-skill`, `aspectQuery=agent-skill.type:system` plus typed system read.
2. Current user's **READY user** publications: `aspect=agent-skill`, `aspectQuery=agent-skill.type:user`, `aspectQuery=agent-skill.userId:<currentUserUUID>` plus actual user source read.
3. Current user's **installations**: `aspect=agent-skill-installation`, `aspectQuery=agent-skill-installation.userId:<currentUserUUID>` plus actual install read. Resolve each `sourceSkillId` and independently authorise/read the original READY source/ZIP.

Merge into one *effective* manifest including source ID, effective alias, checksum and/or relevant source metadata for validation; do not create copied ZIPs. Filter `READY` source states, enforce userId-vs-ID invariants, handle source revocation and validate ZIP before extraction. `optionalAspect` is **not** a mandatory OR filter; Registry forbids `orderBy` plus `pageToken`; paginate each query through completion without incorrectly treating distinct sources as one continuation.

**Workspace usability is independent of skill sync.** Provision essential KAS claim/DSH/current-user credential/bootstrap separately, report Workspace READY and expose standard DSH even when *one, many or all* skills cannot be synchronized, including transient Registry/Storage/OPA outages. Skill resolution failures are **best effort**, not a Workspace-start gate. Skip revoked/missing/invalid sources individually and keep other skills; an infrastructure-wide failure must be marked degraded/failed **for skill sync** rather than falsely reporting zero skills as successful. Failed authorization cannot activate a new unverified skill. Expose sanitized status (e.g. `success`, `partial`, `failed`, `notAttempted`), counts and safe per-skill diagnostics via a small **MAGDA Agent Workspace UI** banner/status area (preferred to forking DSH). **Accepted follow-up (#3857):** expose **Retry / Re-check skill sync** on the MAGDA Open Workspace page for partial/failed status. The authorized Agent Manager—not an arbitrary CLI or client-provided result—re-executes sync in the caller's active Sandbox, validates and persists a new status via claim UID/READY preconditions, and leaves READY/DSH access untouched on failure. A local-computer `mgd agent-skill sync` updates local files only; an independent manual sync inside DSH need not mutate the Manager's last-run status until Re-check. Prevent concurrent Manager retries and cross-user/stale-claim updates. The Stage #3855 bootstrap/exec/claim annotations are sufficient foundations; #3857 owns new authenticated retry endpoint and UI, coordinated with `agentWorkspace/access` (#3858). No new Stage-2 endpoint required. Preserve normal DSH access irrespective of sync errors. On a later **successful** reconciliation, remove stale revoked/removed synced copies; continuous active-workspace revocation monitoring is not an MVP requirement. Already downloaded copies may remain until reconciliation, an explicit accepted trade-off.
